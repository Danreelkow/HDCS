### Sync Hermes Context Directory

**Objective:**
To deliver a standing synchronization of the Hermes context directory using rsync and systemd user units, ensuring that the destination directory mirrors the source directory exactly.

**Details:**

- The source directory is `/opt/data/workspace/hermes-context/`.
- The destination directory is `/workspace/hermes-context/`.
- The synchronization will use rsync as the primary tool, with `cp -a` as a fallback.
- A dry-run mode is available that performs no actual writes.
- Systemd user units will manage the synchronization schedule without requiring root access.
- The synchronization will be idempotent and log a one-line summary after each run.
- The process includes a verification step before finalizing the destination directory.
- The synchronization ensures that the source directory's contents, structure, and symlinks are mirrored exactly in the destination directory, excluding metadata, timestamps, and hardlinks.
- The systemd timer will run the synchronization every 6 hours.
- The process guards against destructive operations by ensuring that source and destination paths are distinct and verifying the integrity of the synchronization.

**Key Points:**

- Source path: `/opt/data/workspace/hermes-context/`
- Dry-run mode: performs no writes
- Systemd user units: no root access required
- Synchronization direction: one-way from host to workspace
- Scheduler: systemctl --user timer
- Mirror semantics: exact mirror, including deletion of stale files
- Dry-run scope: no writes, including logs
- Equivalence class: contents, structure, and symlinks only
- Destructive-op guards: source and destination paths are distinct, verification step, and refusal of degenerate paths
- Owned-path placement: concrete owned paths outside the destination directory
- Environment override: no restrictions, defaults are production values

**Workflow:**

- The workflow includes planning, building, verifying, and delivering phases.
- The builders are dynamic, and the verifier is decorrelated.
- The gate status is either READY or NOT_READY.
- The maximum fix cycles allowed are 2.
